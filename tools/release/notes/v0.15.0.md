## Backups, packages to share, and label icons

This release brings **backups that hold everything**, on any database: the rows and the uploaded files, in one archive you can read without bam. You can also share part of an instance as a **package**: a category with its fields, templates and icons, say, imported into another. Uploaded files can live in an **S3-compatible bucket**. And a category can have a **label icon**, drawn to print well in black and white, beside the icon it shows on screen.

### Backups
- **`bam backup` writes an archive:** a gzipped tar of every row and the uploaded files they name, readable with `tar` and any JSON parser. It works the same on SQLite, PostgreSQL and MariaDB, and needs no `pg_dump`-style commands. It is consistent at one moment while the server keeps running.
- **`bam restore` puts one back:**
  - **Into a new instance**, on any database, whichever one the backup came from, so a backup is also the way to move between databases.
  - **Checked first:** every byte is checked against the archive's manifest before anything changes, so a corrupted or cut-short archive changes nothing. `--check` only checks.
  - **A copy of a SQLite database** made by an older bam is still restored as before.
- **From the web:** **Admin › Backups** downloads a backup. It can also replace chosen kinds of what an instance holds (the catalog, assets, icons, people and so on) with a backup's, after checking it and asking you to type the instance's host. `bam restore --replace` does the same from the command line.
- **Archives of any size:** archives of many gigabytes go up and down over the web in parts, resuming where a dropped connection left off.
- **No one is signed out,** and passwords and other secrets never go through the web.

### Packages to share
- **Exporting:** **Admin › Import & export** packages part of an instance with everything it needs: categories (alone or with those under them), fields, actions, link types, label and scan templates, reports, flows, scopes and icons, and optionally assets with their photos, links and history. A package carries a name, description, author, license, version and a preview image.
- **Importing:** a package is merged into an instance under a category you choose.
  - **Checked first:** the check says exactly what importing will do: create each thing, use the one already here, import a copy under a new name, or skip it, with the permissions it needs. What clashes is yours to choose.
  - **All or nothing:** it then imports as checked, or not at all.
- **Parts of a backup** can be merged into an instance in use the same way.
- **From the command line and assistants:** `bam export` and `bam import`, the API and the MCP tools `check_import` and `import_package`.

### Icons
- **Label icons.** An icon that reads well on screen often prints as noise on a black-and-white thermal label. A category can now have a **label icon** too, best as flat line art:
  - **Drawing one:** on the category's page, under **Icon › On labels**. A preview shows it as it prints, shaded and as an outline, at a label's size.
  - **Where it comes from:** labels print each asset's label icon, from its nearest category with one, as for its screen icon. With none, they print the screen icon, so nothing changes until you draw one.
  - **An asset's own:** an asset can have a label icon of its own.
  - **Templates:** a template's icon can ask for the screen icon instead.
- **isolex studio:** icons move between bam and isolex studio as an isolex library folder.
  - **Out:** **Export as a zip** on the Icons page, and a package of the icons alone, write the folder: `lexicon.ilx` with the palette, `library/`, `categories/` and `icons.json`.
  - **In:** a library folder edited in the studio imports back under **Admin › Import & export**. What changed is replaced, colors and categories' icons included, and the rest is left alone.
- **isolex 0.6.0** compiles the icons.

### Uploaded files
- **In a bucket:** uploaded files (asset photos and label images) can be kept in a bucket of any S3-compatible store, such as AWS, MinIO, Garage, Ceph, Backblaze B2 or Cloudflare R2. Set `[storage] backend = "s3"` and `[storage.s3]`, or the `BAM_STORAGE_S3_*` variables. With PostgreSQL or MariaDB, an instance then keeps nothing on its own disk.
- **Moving them:** `bam storage copy --to <config>` copies every file to another store, checking each, so an instance can move from a directory to a bucket and back.
- **Kept in step with the database:** files no row names are removed after a day, and rows whose file is missing are logged, at startup and every six hours. `bam storage sweep` does it once; `--dry-run` only reports.

### Fixed
- **The Users and Tokens pages** listed a person's or token's roles in no particular order. They now list them by name, as the account page does.

### Upgrading
- **Migrations:** `046` and `047` run when the service starts. `047` rebuilds the category icon tables with a rendition, and every icon you have becomes the screen icon. It changes nothing you see.
- **The updater (`bam-update`) backs up with an archive:** from now on it uses the installed bam's `bam backup` and, if the update fails, `bam restore --wipe`, on every database, uploaded files included. The first update from v0.14.0 still backs up as v0.14.0 did. Backup and restore commands you set by hand are still used in their place.
- **Scripts that run `bam backup`** now get an archive (`.bam.tar.gz`) rather than a copy of the SQLite database. `bam restore` takes either.
- **Uploaded files** stay in `storage.local_path` unless you choose a bucket: `[storage] backend` is `"local"` unless set. The example configurations show both.
- **Nothing else to do.** Existing icons, templates, labels and API calls keep working as they did. An API call that gives no rendition means the screen icon.
